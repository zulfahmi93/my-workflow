u60-monitor — Numeric-text content transitions (plan-007)

Replace the first-load-only count-up ramp with a faithful SwiftUI `.contentTransition(.numericText())` morph that fires on EVERY value change, applied to every live numeric readout in the app. The motion is decoded FROM PIXELS (a 169-frame frame-by-frame capture, `docs/rnd/swiftui-numerictext-animation/`): each changed glyph column does blur + scale + downward slide + asymmetric cross-fade, digits resolve left-to-right (a stagger), and the number width reflows on a digit-count change. The enter-live '0'-baseline count-up hack is removed. ZERO new pubspec deps.

10 / 10 shipped · 3 batches PLAN-008

u60-monitor — Live speed from cumulative counters (plan-008)

The headline DL/UL number is not live: the app displays the agent's `rx_speed`/`tx_speed`, which is a ~15-second rolling mean, so a burst takes ~15 s to register and ~15 s to decay. This plan derives the rate IN-APP by differencing the cumulative `rx_bytes`/`tx_bytes` counters that `SpeedSnapshot` already parses and nothing consumes. Because the counter only advances on the agent's own 1 Hz sampler grid, a 1 Hz client poll provably cannot recover the elapsed tick count (`T_c + δ < 470 ms` has no solution at 1 Hz) and aliases into a ±100% flap — so the speed lane OVERSAMPLES at 250 ms, re-anchors only when a counter actually moves, and divides by the exactly-recovered integer tick count `round(elapsed.inMilliseconds/1000).clamp(1,3)`. Oversampling never escapes the new pure-Dart `SpeedRateDeriver`: holds are suppressed and stale readings throttled, so the UI stream and the history ring keep today's ~1 Hz cadence and `SpeedHistory` is not modified at all. The agent's averages are retained as a one-sample seed/fallback on five guarded paths. 10 cycles, none security-tier. ZERO new pubspec deps.

0 / 6 shipped · 3 batches PLAN-010

u60-monitor — Morph fidelity (plan-010)

plan-007 spent ten cycles building a frame-accurate numeric morph, and on five surfaces it silently does not run. `ADR-0014:179-187` is a forward-lock: unit-bearing single-number surfaces MUST pass the CLEAN numeric run with the unit as a static sibling. At HEAD every named exemplar violates it — `'$percent%'`, `'PEAK $peakLabel'`, `'CAP ${pct}%'`, `'−N dBm'`, `'OF ${formatBytes(limit)}'` and the two `formatBytes` volume readouts all reach the primitive as combined strings, `double.tryParse` fails, `direction == 0`, and `didUpdateWidget` returns without starting the ticker. The result is a whole-string cross-fade where digits should roll. No test fails; the effect just quietly stopped working, and `plan-007.yaml:83` states the CONTRADICTING rule so a reader hits wrong guidance first. Also: `_shrinkOverlay` paints unclipped into negative x with no assertion on where it lands, and `_kHeadroom = 1.12` is type-level unreachable while ADR-0007 still calls it live design. 7 cycles. ZERO new deps.

u60-monitor — Data truth & auth hardening (plan-011)

Four security-tier cycles and one data-truth cycle, all verified at HEAD 1ef8038. The app renders a live data cap for a plan the firmware may consider INACTIVE, because `parsePlan()` models three of the four fields the agent emits and never reads `enabled` — a never-lie violation that fails soft only because this device happens to report `enabled:true`. `saveBaseUrl` is a bare `_storage.write` with zero validation and `AgentClient`'s constructor is an unguarded `Uri.parse`, so the ADR-0002 binding invariant — re-carried unfulfilled by six consecutive plans — is still undischarged; this plan lands the validator DEFENSIVELY, with no setter UI, and retires it permanently. `agent_client.dart:161` documents in its own words that the single-flight login guard is safe only under an unenforced one-client-per-credential assumption and 'needs revisiting'; neither closure route was ever taken. And `build.gradle.kts:30-32` still signs release builds with the shared debug key under a live TODO, which blocks any real distribution. 5 cycles, 4 security-tier. ZERO new deps.
