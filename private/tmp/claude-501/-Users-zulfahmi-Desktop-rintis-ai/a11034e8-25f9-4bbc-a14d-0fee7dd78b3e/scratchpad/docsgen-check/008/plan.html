8.2

SpeedRateDeriver steady state — anchor-on-movement + quantized denominator

flutter-expert architect: none

This is the make-or-break cycle. The design is true or it dies here.

Create lib/core/speed_rate_deriver.dart — pure Dart, importing ONLY package:clock/clock.dart, reading.dart, speed_snapshot.dart. Implement RateSource, the DerivedReading record typedef, and SpeedRateDeriver.accept covering the STEADY-STATE path only: steps 1, 3, 6, 7, 9, 11, 13, 14, 16 of the locked guard order (§Locked design). The defensive branches (4, 5, 8, 10, 12, 15) land in 8.3; publish-gating for stale (step 2) lands in 8.4. Implementing them early is not a bonus — it makes the RED of 8.3/8.4 impossible to fail honestly.

Behaviour this cycle must prove:

  • Seed. First accept with no anchor emits the agent’s rx_speed/tx_speed verbatim, source: agentAverage, publish: true, and sets the anchor.
  • Hold. A poll where neither counter moved and elapsed < holdCeiling re-emits the previous rates with source: held and publish: FALSE, and does NOT move the anchor.
  • Anchor-on-movement (RULE 1). The anchor moves ONLY on a poll where a counter actually advanced, so every measured window is tick-to-tick.
  • Quantized denominator (RULE 2). span = round(elapsed.inMilliseconds / 1000).clamp(1, 3); clock.now() selects that integer and never divides.
  • Joint anchor. Movement of EITHER counter proves a tick occurred, so a zero delta on the other is a TRUE zero. Pure-download traffic must report upload exactly 0.0 at full responsiveness — no hold, no special case.

The beat regression test is the deliverable that matters (test/core/speed_rate_deriver_beat_test.dart). It must encode:

For a simulated agent grid at T_a ∈ {1000, 1002, 1010} ms, a client at 250 ms with ±40 ms jitter, and a constant true rate R, across a phase sweep of ≥ 20 initial phases covering a full drift wrap: every emitted RateSource.derived value equals R to within 1%. No sample is 0. No sample exceeds 1.5·R.

AND the identical trace fed through an inline naive Δbytes / secondsSincePreviousPoll at T_c = 1000 ms produces at least one sample ≤ 0.5·R and at least one ≥ 1.5·R.

The second half is not decoration — it makes the suite document the failure mode it prevents, and it is exactly what would have caught the halving bug the architect verdict found in a competing design. Drive it under fakeAsync (which installs a fake clock, so clock.now() moves with async.elapse()); the simulated agent grid is a plain helper in the test file, not a new production abstraction.

The RED author MUST read lib/core/reading.dart, lib/core/speed_snapshot.dart and lib/core/speed_history.dart (for the package:clock precedent) BEFORE writing assertions, and assert against the verified types — not against this sketch.

Architecture review. none — The design is fully locked by the pre-plan 4-design/4-judge architect verdict (§Architect verdict, §Locked design): exact file, class name, constructor defaults, the 16-step guard order, both quantization rules, and the arithmetic. Nothing is left for a cycle-level architect to decide. The verdict explicitly states no further architect gates. Correctness is gated by the beat regression test plus an opus code-reviewer pass. NOT security-tier — no auth, secrets, PII or injection surface; it consumes two integers already on the wire.

8.3

Defensive branches — warm-up, decrease, absurd, long gap, backward clock, grid sanity

flutter-expert architect: none

Add the defensive branches to SpeedRateDeriver.accept — steps 4, 5, 8, 10, 12, 15 of the locked guard order. No input may produce a negative, non-finite, or absurd rate.

Step 4 MUST precede step 6, and MUST CLEAR the anchor rather than set it. This ordering is the entire fix for the fabricated-GB/s path and is a named REVIEW must-check. Verified reachable: SpeedTracker::new seeds latest to all zeros including elapsed_ms: 0, and the background thread only overwrites after its first sleep(1s) AND buf.len() >= 2 — so for up to a second after any agent restart the endpoint returns HTTP 200 with rx_bytes: 0. Anchoring there and differencing on the next poll prints gigabytes per second into a PEAK label with a two-minute memory.

Branches, each with its own test:

Step Condition Emitted
4 snapshot.elapsedMs == 0 (agent warm-up) isStale: true, error: null, source: none, publish: true, anchor CLEARED
5 elapsedMs >= 14000 && (elapsedMs/15 - 1000).abs() > 150 (grid broken) re-anchor, agent average
8 dRx < 0 || dTx < 0 (counter reset/decrease) re-anchor, agent average — guarded BEFORE any division
10 elapsed < Duration.zero (clock stepped back) re-anchor, agent average
12 elapsed > maxSpan (long gap) re-anchor, agent average
15 non-finite, or either rate > absurdBytesPerSec re-anchor, agent average — NEVER clamp

Rulings that must survive REVIEW unchanged:

  • No wrap-correction on decrease. Counter wrap and counter reset are indistinguishable from the client; guessing fabricates 4 GiB of traffic. One fallback sample is the honest answer.
  • Never clamp an absurd value. Displaying a clamped 10 Gbps would be a lie dressed as a measurement. Re-seed instead.
  • error stays null on the warm-up path so the password sheet is not triggered.
  • Both directions re-seed together on reset — it is a device-level event.
  • (0,0)-then-restore must be covered: read_rmnet_bytes() falls through to (0, 0) when both sysfs and /proc/net/dev fail, and one interface dropping out of the two-interface sum subtracts its entire cumulative history. The decrease guard catches the drop; the absurdity ceiling catches the restore.

Also add the true-idle boundary test: a zero delta at < 1750 ms HOLDs, at >= 1750 ms falls through to 0 / round(1.75→2) = 0.0 with source: idle and re-anchors. holdCeiling is bounded below by T_a + T_c + jitter ≈ 1360 ms and above by 2·T_a ≈ 2020 ms; 1750 ms centres that band. Bias high — too low prints a spurious '—' dropout (a lie), too high delays idle convergence (cosmetic).

Architecture review. none — Guard semantics are fully specified by the pre-plan architect verdict’s edge-case table (§Edge-case table), including the load-bearing ordering constraint (step 4 before step 6, clearing rather than setting the anchor) and the explicit no-clamp / no-wrap-correction rulings. No design latitude remains. Gated by an opus code-reviewer pass. NOT security-tier.

8.4

Publish gating — 4 Hz in, ~1 Hz out

flutter-expert architect: none

Add step 2 of the guard order — the stale path and its publish throttle — completing SpeedRateDeriver.

The contract: 4 Hz in, ~1 Hz out. Oversampling must never escape the deriver. publish: false means the caller must not forward to the UI stream or the history ring, which is what keeps the published cadence at today’s ~1 Hz while the client samples at 4 Hz. Consequences that must be asserted:

  • Holds suppress, so _speedController and _history see exactly today’s cadence.
  • The .numericText() morph (ADR-0014) fires as often as it does today.
  • The ring still covers ~2 minutes, so ADR-0003’s “120 samples ≈ 2 minutes at ~1 Hz” stays true and SpeedHistory needs no change.

The stale path (step 2), three requirements, each load-bearing:

  1. Substitute the last DERIVED rates into the passed-through stale snapshot. Without substitution the displayed number visibly snaps from the derived value to the agent’s 15 s average at the instant the stale badge appears.
  2. FREEZE the anchor. Poller re-emits the same _last object on failure, so feeding it to the anchor logic would read as a zero delta and wrongly print 0 during an outage.
  3. Throttle to staleThrottle (1000 ms). A 30 s outage must consume ~30 ring slots, not 120 — otherwise a single outage evicts the entire 2-minute window.

The throttle lives inside the deriver, not in _SpeedHomeState. This is an explicit verdict ruling: withClock appears nowhere in test/, so testWidgets runs clock.now() on real wall time — a widget-layer throttle would be wall-clock nondeterministic and flake on slow CI. Inside the deriver it sits under fakeAsync and is exactly deterministic.

Assert the end-to-end cadence property directly: feed a 4 Hz trace over a simulated minute and assert the published count is ~60, not ~240.

8.10

Human on-device pass (iOS + Samsung S22)

human architect: none no TDD cycles

Eight items no automated test can substitute for. Pre-declare the intentionally higher, spikier PEAK in the cycle note BEFORE the pass — it is the single most likely false regression report.

  1. Battery cost of 4 Hz polling. The one real cost of this design. The agent side is cheap (sample() is a lock + clone) and the radio is already continuously active at 1 Hz, so the marginal cost should be packet processing — but that is reasoning, not measurement on this hardware. If it fails, the mitigation is 8.9’s lifecycle pause, NOT a slower poll.
  2. IPA counter batching — the biggest unknown. The agent’s own comment at system.rs:272 reads “ring buffer + background sampler for IPA batch smoothing.” That is the original author saying the ring exists because the hardware-offload counter (rmnet_ipa0) flushes in batches. If the flush period is ~1–2 s, per-tick byte deltas are intrinsically lumpy at the source, and no client-side scheme can recover timing that was never sampled. Capture 60 s of raw per-tick deltas over the real modem during a sustained transfer. If batching is real, the honest outcome is a smaller responsiveness win than promised, and the fix is a 2-tick window — not more machinery.
  3. The real agent sampler period and its stability under sustained high throughput (sleep(1s) + 4 sysfs reads + contention from the modem’s own NAT/daemons). This sets whether holdCeiling = 1750 ms is right. Symptom of it being wrong: an occasional single-frame dropout to '—' at low traffic.
  4. Whether rmnet_data0 + rmnet_ipa0 DOUBLE-COUNT. On Qualcomm, ipa0 is often the accelerated aggregate the muxed dataN interfaces ride on. If so, absolute rates are ~2× wrong both before and after this change — a pre-existing defect this change makes more visible by sharpening bursts, so it may get misattributed here. Cross-check one derived reading against a Speedtest run.
  5. Whether the sysfs counters are 32-bit and wrap. At 100 Mbps a 32-bit unsigned long wraps every ~5.7 minutes. The decrease guard handles it correctly (one fallback sample), but the frequency determines whether that is invisible or annoying.
  6. Real LAN latency spread δ, and whether the agent’s httpd serialises. Six pollers share one AgentClient; four fire together every 10 s. If the agent serialises, the speed poll gets a correlated, periodic latency spike — a 10 s-period ripple no unit test can surface, which would look exactly like a bug in this new code.
  7. Whether the .numericText() morph (ADR-0014) still fires cleanly. Publish-gating should keep the UI stream at ~1 Hz so morphs fire exactly as often as today, but it was not traced whether NumericTransition / SpeedTwin retrigger on rebuild versus on value change. Confirm no animation restarts mid-flight.
  8. Whether ~1 s actually feels live, and whether the sharper trace reads as informative or jumpy. The displayed value now moves meaningfully every second instead of gliding. That is the stated goal, but only a pixel-level pass validates it. Also assess whether the taller auto-ranged axis flattens the baseline — that is a separate chart-scaling question, explicitly out of scope, and must be filed as its own plan rather than bundled.

Capture evidence to docs/rnd/plan-008-device-pass/ (screen recordings, battery readings, the 60 s delta capture) following the plan-007 batch P7.C precedent.

Architecture review. none — Not a code cycle — a human measurement and observation pass on physical hardware. No diff, no tests, nothing to gate architecturally. Two of its findings can send the plan BACK to the architect (see §Stop conditions): a failed battery reading and confirmed IPA batch smoothing. NOT security-tier.
