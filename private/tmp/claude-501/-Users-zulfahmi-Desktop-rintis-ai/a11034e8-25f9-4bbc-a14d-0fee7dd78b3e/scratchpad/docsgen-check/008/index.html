Build plan 008

u60-monitor — Live speed from cumulative counters (plan-008)

The headline DL/UL number is not live: the app displays the agent’s rx_speed/tx_speed, which is a ~15-second rolling mean, so a burst takes ~15 s to register and ~15 s to decay. This plan derives the rate IN-APP by differencing the cumulative rx_bytes/tx_bytes counters that SpeedSnapshot already parses and nothing consumes. Because the counter only advances on the agent’s own 1 Hz sampler grid, a 1 Hz client poll provably cannot recover the elapsed tick count (T_c + δ < 470 ms has no solution at 1 Hz) and aliases into a ±100% flap — so the speed lane OVERSAMPLES at 250 ms, re-anchors only when a counter actually moves, and divides by the exactly-recovered integer tick count round(elapsed.inMilliseconds/1000).clamp(1,3). Oversampling never escapes the new pure-Dart SpeedRateDeriver: holds are suppressed and stale readings throttled, so the UI stream and the history ring keep today’s ~1 Hz cadence and SpeedHistory is not modified at all. The agent’s averages are retained as a one-sample seed/fallback on five guarded paths. 10 cycles, none security-tier. ZERO new pubspec deps.

10 TDD cycles 5 parallel batches Low — the spine is inherently serial. 8.2→8.3→8.4 are the SAME file (speed_rate_deriver.dart) and strictly ordered; 8.5→8.6→8.7 is an ordering chosen deliberately so a harness break, a wiring break and a cadence break stay distinguishable. 8.1 (docs) and 8.8 (format.dart + speed_screen.dart) are genuinely file-disjoint from the deriver cycles and could parallelize in worktrees, but the run executes SEQUENTIALLY on main because each cycle's full-suite `flutter test` gate is cross-attributable in a shared tree (the plan-004/005/006 lesson). Roughly 10 commits, one per cycle. wall-time saved 4 / 10 shipped

Context

The defect. The project guide previously stated that GET /api/network/speed’s rx_speed/tx_speed are “a rolling ~1s average of rmnet_data0”. Both halves were wrong, and the misconception is what hid the bug for seven plans.

Verified in the agent source (open-u60-pro/zte-agent/src/system.rs:272–380, a separate repo this project never modifies):

  • SPEED_RING_SIZE = 16. A background thread samples /sys/class/net/{rmnet_data0,rmnet_ipa0}/statistics/{rx,tx}_bytes once per second into a 16-slot ring.
  • rx_speed = (newest.rx_bytes - oldest.rx_bytes) / secs, i.e. a mean over the whole ring. A 16-slot ring spans 15 intervals, so the window is ~15 s, not ~16 s — the agent’s own inline comment // 16 samples × 1s = 16s window is off by one. Use elapsed_ms / 15 for any period arithmetic, once elapsed_ms ≥ ~14 000 — a deliberately conservative gate, not “the ring is full”: a fully-filled 16-slot ring spans 15 intervals and reaches elapsed_ms ≈ 15 000, whereas ~14 000 is 15 samples spanning 14 intervals, one slot short. During the ~15 s fill after an agent restart the ring holds n<16 samples spanning n-1 intervals, so elapsed_ms/15 understates the per-tick period.
  • It sums two interfaces (rmnet_data0 + rmnet_ipa0), not rmnet_data0 alone.
  • elapsed_ms is that same ~15 000 ms window, not a per-tick interval.

The app polls at 1 Hz and displays that mean. So the “live” number ramps over ~15 s, peaks after the burst has already ended, and decays for ~15 s afterwards. Short bursts barely move it. SpeedSnapshot.rxBytes / txBytes / elapsedMs are already parsed (lib/core/speed_snapshot.dart:23-25) and consumed by nothing in lib/.

The fix, and why it is not a one-liner. Differencing a cumulative counter is arithmetic. The trap is the denominator.

The numerator is exact — rx_bytes is a monotone kernel counter, so no bytes are lost or double-counted however the client and agent grids interleave. But the counter the app receives is quantized to the agent’s 1 Hz sampler and is up to 1 s stale at request time: it is newest.rx_bytes from the agent’s ring, sampled by the agent’s own thread, not read at request time. A poll at time p therefore observes the counter as of the latest agent tick a_k ≤ p, with detection lag φ = p − a_k ∈ [0, T_c + δ).

Anchoring on tick i and observing the next movement on tick j:

t_j − t_i = (j−i)·T_a + (φ_j − φ_i)

round((t_j − t_i)/1000) recovers (j−i) exactly iff |(j−i)·(T_a − 1000) + (φ_j − φ_i)| < 500 ms. With (j−i) ≤ 3 and T_a − 1000 ≤ 10 ms the drift term is ≤ 30 ms, so the condition collapses to the ruling inequality:

T_c + δ < 470 ms

At T_c = 1000 ms this fails outright — that failure is the beat: some polls see no counter change (rate reads 0), the next sees two ticks’ worth (rate reads ~2×). A naive Δbytes / secondsSincePreviousPoll at 1 Hz would ship a number that flaps ±100%, which is worse than the status quo. At 500 ms it still fails; at 333 ms the margin is 37 ms — not admissible. Admissible range is T_c ≤ 300 ms; locked at 250 ms (margin 120 ms at δ = 100 ms).

So the cadence change is not an optimisation. It is the enabling condition, and there is no cheaper cadence that preserves correctness.

Two rules, both required. RULE 1 — the anchor (rxBytes, txBytes, localTime) moves only on a poll where a counter actually advanced, so every measured window is tick-to-tick, never poll-to-poll. RULE 2 — the denominator is the recovered integer tick count round(elapsed.inMilliseconds/1000).clamp(1,3), never the raw wall interval; clock.now() is used only to select an integer and never divides. In steady state the elapsed time between anchor moves is T_a ± T_c = 1.002 ± 0.25 s, which always rounds to 1 — the anchor rides the agent’s grid, so there is no phase to wrap. The beat is structurally impossible, not damped.

One joint anchor, not two. rx and tx come from the same agent sample, so movement of either counter proves a tick occurred, which makes a zero delta on the other counter a true zero (a tick that carried no bytes) rather than an unobserved tick. Pure-download traffic therefore reports upload = 0.0 exactly, at full responsiveness, with no hold and no per-direction machinery.

Two real fabrication paths the guards exist to close — both verified reachable in the agent source, neither hypothetical:

  1. SpeedTracker::new seeds latest to all zeros including elapsed_ms: 0, and the background thread only overwrites after its first sleep(1s) and buf.len() >= 2. So for up to a second after any agent restart, GET /api/network/speed succeeds (200) and returns rx_bytes: 0. Naive differencing then sees 0 → <full cumulative counter> and prints gigabytes per second into a PEAK label with a two-minute memory. elapsed_ms == 0 is an exact fingerprint for this (after the first tick it is ≥ 1000 even at literal zero traffic), and the warm-up poll must clear the anchor rather than become one.
  2. read_rmnet_bytes() sums two interfaces under a per-interface if let (Some, Some) guard and falls through to (0, 0) when both sysfs and /proc/net/dev fail. One interface dropping out subtracts its entire cumulative history from the sum; a total read failure gives 0-then-restore. Both are decreases followed by large positive jumps.

Guards are ~10 lines. But a design that ships without them replaces a slow-but-true number with an occasionally confident lie, which is the never-lie rule inverted.

Architect verdict — the gate for this plan

A 4-design / 4-judge panel produced a binding architect verdict before this plan was authored. It verified every load-bearing claim against zte-agent/src/system.rs, lib/, and test/ rather than accepting the design briefs, and it overruled two of the four judges on evidence:

  • Overruled the correctness judge (which picked the “Grid-Lock” design): its blast-radius evidence was fabricated — it claimed speed_twin_test.dart (55), speed_history_chart_test.dart (50), format_test.dart (26) survive untouched; the real counts are 16, 34, 27. Blast radius was precisely the axis on which that design asked to be trusted. Separately its windowTicks = 2 boxcar gives away half the responsiveness win to reduce variance the exact-numerator argument shows is not there.
  • Overruled the testability judge (which picked the “State Machine”): it ships a halving bug in the dominant beat direction, and its regression test is rigged to the other one. At each phase wrap two consecutive polls fall inside one agent interval → delta == 0 → HELD freezes the window → the next poll sees one tick’s bytes over a 2.0 s accumulated window → snaps to span 2 → emits R/2. Its test hard-codes [+N, +N, +0, +2N, +N], which presupposes the client-slower case. The suite would go green while the device periodically halves the number.

Winner: the minimalist design, with four grafts — the elapsedMs == 0 warm-up fingerprint (from skeptic), the absurd-value ceiling that re-seeds rather than clamps (grid-lock + skeptic), the grid-sanity guard (state-machine’s risk #1 made concrete), and RateSource + publish provenance on the result record (grid-lock + state-machine). Plus one improvement on all four: the stale-publish throttle moves into pure core, because withClock appears nowhere in test/, so a widget-layer throttle would be wall-clock nondeterministic and flake on slow CI.

Rejected on evidence: a LiveSpeed wrapper type (propagates through _speedController, SpeedHistory’s type parameter and five speed_screen.dart sites, and by its own admission forces pump-timing rewrites in app_flow_test.dart — the most flake-prone churn available, spent on a type rename); extra fields on SpeedSnapshot (blurs a wire DTO); a reset() on the deriver (dead code — see the re-login row in §Edge-case table); bumping SpeedHistory.capacity to 480 (changes a public API and quadruples painter work for zero benefit).

The locked design — SpeedRateDeriver

NEW lib/core/speed_rate_deriver.dart — pure Dart, imports only package:clock/clock.dart, reading.dart, speed_snapshot.dart.

/// Provenance of an emitted rate. Exposed on the result record so tests
/// assert WHY a value was emitted, never reverse-engineer it from the number.
enum RateSource {
  agentAverage, // seed / re-seed — the agent's ~15 s rx_speed, verbatim
  derived,      // one agent-second of bytes ÷ an exactly-recovered tick count
  held,         // counter has not ticked yet — previous value re-emitted
  idle,         // a tick provably carried zero bytes
  none,         // agent warm-up — no trustworthy value exists
}

/// One result of [SpeedRateDeriver.accept].
///
/// [publish] false means SUPPRESS: the caller must not forward to the UI
/// stream or the history ring. This is what keeps the published cadence at
/// ~1 Hz while the client samples at 4 Hz.
typedef DerivedReading = ({
  Reading<SpeedSnapshot> reading,
  bool publish,
  RateSource source,
});

class SpeedRateDeriver {
  SpeedRateDeriver({
    this.holdCeiling       = const Duration(milliseconds: 1750),
    this.maxSpan           = const Duration(milliseconds: 3000),
    this.staleThrottle     = const Duration(milliseconds: 1000),
    this.agentPeriod       = const Duration(milliseconds: 1000),
    this.periodTolerance   = const Duration(milliseconds: 150),
    this.absurdBytesPerSec = 1.25e9, // 10 Gbps — impossible on sub-6 5G
  });

  final Duration holdCeiling, maxSpan, staleThrottle, agentPeriod, periodTolerance;
  final double absurdBytesPerSec;

  /// Feed EVERY poll, success and stale. Reads `clock.now()` exactly once.
  DerivedReading accept(Reading<SpeedSnapshot> raw);
}

Internal state, five fields for 8.2’s steady-state path: int? _rxAnchor, _txAnchor; DateTime? _anchorAt; double _lastDown = 0, _lastUp = 0;. A sixth field, DateTime? _lastPublishAt, joins in 8.4 with the stale-publish throttle (step 2). No reset(). No copyWith on SpeedSnapshot — its 5-field const constructor is called inline at the one substitution site.

Guard order inside accept — load-bearing. Step 4 MUST precede step 6, and MUST clear the anchor rather than set it. That ordering is the entire fix for the fabricated-GB/s path: the warm-up poll never becomes an anchor, so the following poll re-seeds against the real counter instead of differencing against 0.

 1  snapshot == null                    → passthrough,          publish=true
 2  raw.isStale                         → substitute _last rates, anchor FROZEN,
                                           publish = (now - _lastPublishAt >= staleThrottle)
 3  now = clock.now()
 4  snapshot.elapsedMs == 0             → AGENT WARM-UP: CLEAR the anchor, emit the
                                           reading marked isStale:true (error stays null),
                                           source=none,          publish=true
 5  elapsedMs >= 14000 &&
    (elapsedMs/15 - 1000).abs() > 150   → GRID BROKEN: re-anchor, agent average, publish=true
 6  _anchorAt == null                   → SEED: anchor, agent average,  publish=true
 7  dRx = rx - _rxAnchor; dTx = tx - _txAnchor
 8  dRx < 0 || dTx < 0                  → RESET: re-anchor, agent average, publish=true
 9  elapsed = now - _anchorAt
10  elapsed < Duration.zero             → CLOCK STEPPED BACK: re-anchor, agent avg, publish
11  dRx == 0 && dTx == 0 &&
    elapsed < holdCeiling               → HOLD: re-emit _last, source=held, publish=FALSE
12  elapsed > maxSpan                   → LONG GAP: re-anchor, agent average, publish=true
13  span = (elapsed.inMilliseconds / 1000).round().clamp(1, 3)
14  down = dRx / span;  up = dTx / span
15  !finite || down > absurd || up > absurd
                                        → ABSURD: re-anchor, agent average, publish=true
16  → DERIVED (source=idle if both are exactly 0): re-anchor, publish=true

Wiring — lib/app.dart, _onSpeedData becomes six lines:

void _onSpeedData(Reading<SpeedSnapshot> reading) {
  final d = _deriver.accept(reading);
  _checkAuthError(reading.error);          // ALWAYS — outside the publish gate
  if (!d.publish) return;
  if (!_speedController.isClosed) _speedController.add(d.reading);
  _history.add(d.reading);
  _historyNotifier.value = _history.samples;
}

_checkAuthError outside the gate is non-negotiable and a named REVIEW must-check: it currently sits at the tail of _onSpeedData (line ~403), so gating it behind publish would delay auth-halt recovery by up to a second. final _deriver = SpeedRateDeriver(); is a _SpeedHomeState field created in initState, a sibling of late final SpeedHistory _history (line ~256).

Worked steady-state trace — agent ticking at t = 0, 1.002, 2.004; client at 250 ms:

t=0.00  seed, anchor=(C₀, 0.00)
t=0.25  δ=0 → HOLD (publish=false)
t=0.50  δ=0 → HOLD
t=0.75  δ=0 → HOLD
t=1.00  δ=0 → HOLD                     ← tick 1 lands at 1.002, not yet visible
t=1.25  counter moved → elapsed 1.25 → round 1 → rate = ΔB/1  EXACT. re-anchor.
t=2.25  counter moved → elapsed 1.00 → round 1 → EXACT.

Dropped poll: recovery at +1.50 s → round → 1 → still exact. Two ticks in one gap (GC, backgrounding): elapsed ≈ 2.0 → round → 2 → a correct 2-second average. Both degrade rather than spike.

SpeedHistory, chart and PEAK ruling

lib/core/speed_history.dart is NOT modified. No capacity change, no API change, no new field; its 10 existing tests are untouched. Because the deriver publishes at ~1 Hz, the ring fills at ~1 Hz, the window stays ~2 minutes, formatElapsedWindow still reads ≈ −2:00, and ADR-0003’s “120 samples ≈ 2 minutes at ~1 Hz” remains true as written.

PEAK will read materially higher. This is INTENDED and it is a bug fix, not a regression. Today’s PEAK is the max of a 15 s mean, which systematically under-reports: a 2 s burst at 500 Mbps inside a 15 s window is reported at roughly 67 Mbps (500 × 2/15). Calling that a “peak” is arguably the pre-existing defect. peakBytesPerSec needs no code change. The trace becomes spiky where it was smooth, and the painter’s auto-ranged axis ceiling will re-range more often.

Mandatory: the 8.10 cycle note must PRE-DECLARE the higher, spikier PEAK. This is the single most likely false regression report on the device pass.

Gap-marker contract: mechanism unchanged, producer set extended. ADR-0003 defines gap markers as poll failure (snapshot == null || isStale). This adds one new producer: agent warm-up (elapsed_ms == 0). isStale is ruled to mean “no trustworthy current value” — which already covered poll failure and now covers a poll that succeeded but carried nothing usable. The alternative is a nullable rate threaded through Reading, SpeedHistory.add and speed_screen’s freshness machine to describe a state that lasts ≤ 1 s after an agent restart. The chart’s break is the correct rendering of “the agent doesn’t know yet.”

One display fix is mandatory, and it is not scope creep. format.dart:48 is literally if (bytesPerSec <= 0 || bytesPerSec.isNaN) return ('—', '', ''). That contract was written when 0 could only mean a corrupt poll. Once we derive, exact 0 is a legitimate, frequent measurement — “this second carried no bytes” — and WAN keepalive/DNS traffic will alternate 0 ↔ ~200 B/s at idle, flickering the headline numeral between '—' and '1.6 Kbps' roughly every second, on the most-looked-at pixel, aggravated by the ADR-0014 '—'→digit morph special case.

But splitRate must NOT be rewritten. Making 0 → ('0','','bps') there would also change the PEAK label on an empty or all-stale ring, where peakBytesPerSec returns 0.0 and '—' is genuinely correct. Instead (cycle 8.8): add splitMeasuredRate(double) to format.dart returning ('0', '', 'bps') for exactly 0 and delegating to splitRate otherwise. splitRate is unchanged, so format_test.dart:146–153 stays green and the PEAK/empty-ring path keeps '—'. Only speed_screen.dart’s _splitRate (line ~183, the live DL/UL numerals) switches to it; its own snapshot == null → '—' guard at line 179 is untouched. Zero existing tests break.

Latent test-harness defect (must land before wiring)

The verdict found a genuine pre-existing defect in the test harness that no previous cycle exercised, because nothing consumed the byte counters:

test/support/fake_agent.dart:240, test/support/fake_multi_client.dart:266 and test/app_flow_test.dart:119 all return a frozen rx_bytes: 10000 alongside rx_speed: 1250000.0 — mutually contradictory (1.25 MB/s against a counter that never moves). Under the deriver they present as permanently idle.

All three must advance their counters (rx_bytes += 1250000, tx_bytes += 625000 per speed request), which reproduces today’s advertised 10/5 Mbps by construction.

Cycle 8.5 fixes this BEFORE the 8.6 wiring lands. Ordering is not cosmetic: with the harness broken, a harness failure and a wiring failure are indistinguishable, and the debugging cost of that ambiguity is the whole reason the cycle exists separately.

This also neutralises a flake hazard. withClock appears nowhere in test/, so testWidgets runs clock.now() on real wall time. With advancing counters the derived rate equals the advertised rate on every branch: real elapsed ≈ 0 → clamp(1) → 10 Mbps; slow CI past 1.75 s → span 2 → 5 Mbps; past 3 s → re-seed → 10 Mbps. All three satisfy findsWidgets on 'Mbps' and findsNothing on '0.0 Mbps'.

  • pure-Dart lib/core boundary upheld — speed_rate_deriver.dart imports only package:clock/clock.dart, reading.dart, speed_snapshot.dart.
  • ADR-0005 multi-metric polling UNTOUCHED — Poller<T> / Reading<T> unchanged; derivation lives outside the generic poller (inside it would be an instant BLOCKER).
  • ADR-0003 history ring preserved — capacity, timestamps and gap-marker mechanism unchanged; only the producer set grows.
  • ADR-0013(a) immediate-first-tick preserved — the first sample emits the agent average, so no blank frame at launch.
  • ADR-0014 numeric morph preserved — publish-gating keeps the UI stream at ~1 Hz, so morphs fire exactly as often as today (8.10 item 7 confirms on device).
  • never-show-0 / last-known + stale honoured — stale polls substitute the last derived rates and freeze the anchor; a true measured 0 is a different thing and renders as '0 bps' (8.8), never as a fake dropout.
  • never-lie honoured — every path that cannot produce a trustworthy live number falls back to a real measurement (the agent’s 15 s mean) or a gap marker; nothing is clamped, faked, or carried forward silently.
  • ADR-0002 base-URL invariant DORMANT — no base-URL/credential write.
  • no test weakening — only ONE existing assertion changes (app_multipoller_test.dart:65, a cadence constant), and it changes because the constant changed.
  • ZERO new pubspec deps.
