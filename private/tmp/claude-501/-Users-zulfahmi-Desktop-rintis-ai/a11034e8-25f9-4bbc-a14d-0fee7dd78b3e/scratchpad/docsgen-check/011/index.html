Context

Scope is items BUG-3, A1/BUG-8, A6/BUG-7, A15/BUG-5 and A19 of docs/open-issues-2026-07-19.md. Every claim below was re-verified against source while authoring this plan, not taken from the backlog.

1. The app can display a cap for a plan the firmware has turned off (BUG-3). Upstream zte-agent/src/handlers.rs:197-202 emits four plan fields including enabled (from month_limit_enable). lib/core/data_usage_snapshot.dart:168-177 — parsePlan() — reads exactly three: month_limit_bytes, clear_day, remind_percent. Verified: a repo-wide grep for a data-plan enabled in lib/ and test/ returns nothing (the only enabled hits are charge_limit_enabled, a different domain). The UI keys NO-PLAN exclusively on monthLimitBytes == null (data_usage_section.dart:22), so a firmware plan toggled off while month_limit_value remains populated renders a live cap, a percentage, the progress bar and the OVER/red escalation — for a plan the firmware considers inactive. That is a never-lie violation: the app states something about the user’s data plan that the device does not agree with. It fails soft and is unreachable on the current device (enabled:true), but it is silent contract drift against the 5.1 architect lock (cycles/5.1.yaml:53, three fields) that no ADR or follow-up records as deliberate. There is an in-repo precedent for the fix: the battery domain already parses charge_limit_enabled and gates behaviour on it (battery_snapshot_test.dart:11,18,21).

2. The ADR-0002 invariant has been carried by six plans and never discharged (A1). lib/data/credential_store.dart:97 is Future<void> saveBaseUrl(String url) => _storage.write(key: _kBaseUrlKey, value: url); — no scheme check, no host check. The transport boundary is equally open: agent_client.dart:62 is _baseUrl = baseUrl is Uri ? baseUrl : Uri.parse(baseUrl as String). Verified: git log -S"isPrivate" is empty across all history — no validator has ever existed.

The invariant says any cycle adding a UI or path to set a non-default base URL must validate it (http(s) + private/LAN host) in that same cycle, before the Bearer password is sent to it. It is currently dormant and correctly gated — plans 002 through 007 each list a base-URL setter as an out-of-bounds STOP, and saveBaseUrl’s only caller is a test (credential_store_test.dart:67) — but it has now been re-carried, unfulfilled, six times.

This plan takes the third route none of the ten source records proposed: land the validator DEFENSIVELY, now, with no setter UI. That permanently discharges the invariant, retires a “test-only” property currently held by nothing but reviewer vigilance, and de-risks any future settings cycle in advance. The alternative — carrying it a seventh time — is how a dormant invariant eventually gets missed.

3. The single-flight login guard documents its own unenforced assumption (A6/BUG-7). agent_client.dart:155-161, in its own words:

SINGLE-PRINCIPAL ASSUMPTION: a joiner authenticates under whichever password _performLogin read from _passwordProvider when IT started — joiners never re-read the provider themselves. This is safe only because one AgentClient instance serves exactly one credential for one modem; if this client is ever reused across multiple accounts, a joiner could be silently authenticated under a DIFFERENT caller’s password (a confused-deputy risk) and this guard needs revisiting.

Neither closure route was taken. _login() (:162-169) has no principal check, and no test pins the invariant — the two nearest tests (agent_client_test.dart:312, app_multipoller_test.dart:76) pin the sharing, i.e. the risky direction. ADR-0013:53-56 restates the deferral rather than accepting it. The risk is latent, held only by construction discipline (a single fixed storage key; re-auth builds a fresh client at app.dart:275). Either close it or formally accept it with a pinning test — what is not acceptable is a third plan restating the deferral.

4. Release builds are signed with the shared debug key (A15/BUG-5). android/app/build.gradle.kts:26-33, verbatim: // TODO: Add your own signing config for the release build. / // Signing with the debug keys for now, so 'flutter run --release' works. / signingConfig = signingConfigs.getByName("debug"). Unchanged since the cycle-1.1 scaffold. Debug-key APKs use a well-known password and are machine-local; this blocks any real distribution. Half the work is already done — android/.gitignore:12-14 already ignores key.properties, *.jks and *.keystore.

5. A plaintext .env exists (A19). Verified present (43 bytes), correctly gitignored, and read by nothing — there is no flutter_dotenv dependency and the app’s only credential path is flutter_secure_storage. Hygiene, not exposure. Delete it or document why it exists; either is fine, leaving it undocumented is not.

Security-tier ruling

11.1, 11.2, 11.4 and 11.5 ARE security-tier. 11.3 is not.

11.1 — base-URL validation. Edits the credential store (secret material) and the transport boundary the Bearer password is sent to. The invariant’s whole point is that an unvalidated base URL means the password can be sent somewhere it should never go. The architect must confirm: validation runs BEFORE any credential leaves the device; both entry points are covered (saveBaseUrl AND the AgentClient constructor — guarding only one leaves the other open); rejection is explicit failure, never a silent fallback to the default (a silent fallback would mask a tampered store and is the subtler bug); and the LAN-host predicate admits every address the modem can legitimately occupy without admitting a public host.

11.2 — confused deputy. Edits _login()/_performLogin — authentication logic — or formally accepts a documented risk in an ADR. Either outcome is a security decision.

11.4 — release signing. Key material and distribution integrity. The security-reviewer must confirm no keystore, password or key.properties is committed or printed, and that the release build genuinely fails (rather than silently falling back to debug) when the keystore is absent — a fallback would recreate the exact defect while appearing fixed.

11.5 — .env. Touches a file whose name implies secrets. Verified read by nothing, but the disposition is a secrets-hygiene decision and takes the second pass.

11.3 is NOT security-tier. It parses one additional boolean from a response the app already consumes and gates presentation on it. No auth surface, no secret, no injection sink, no new endpoint. Architect gate + REVIEW on opus per the model-tier policy — a quality choice, not a security requirement.

What the base-URL validator must do (11.1)

The architect ratifies the exact predicate; these are the constraints it must satisfy.

Both entry points, or neither is closed. credential_store.dart:97 (saveBaseUrl) and agent_client.dart:62 (the Uri.parse constructor). Guarding only the setter leaves a tampered stored value flowing straight into the client; guarding only the client leaves an invalid value persisted to be re-read forever. The invariant’s wording — validate “before the Bearer password is sent to it” — points at the transport boundary as the load-bearing one.

Scheme: http or https only. Anything else — file, javascript, a scheme-relative or empty scheme — is rejected.

Host: private/LAN only. RFC1918 (10/8, 172.16/12, 192.168/16), link-local (169.254/16), loopback, and the corresponding IPv6 ranges (unique-local fc00::/7, link-local fe80::/10, ::1). A public host is rejected. Decide explicitly whether a hostname (rather than a literal IP) is permitted — a hostname cannot be range-checked without resolving it, and resolving at validation time is both a network call in a validator and a TOCTOU window. Default lean: reject hostnames; the modem is reached by literal IP and the project’s own contract fixes 192.168.0.1:9090.

Rejection is explicit. Throw or return a typed failure. Never silently fall back to the default — a silent fallback means a tampered or corrupted stored URL looks like normal operation, which is strictly worse than a visible failure and is the subtler of the two possible bugs here.

Port: the default is 9090; decide whether other ports are permitted. Leaning permissive here is defensible since the host check is what actually constrains the destination.

This does NOT add a setter UI. Adding one remains out of scope and would be its own security-tier cycle. Landing the validator first is what makes that future cycle routine rather than dangerous.

The invariant is discharged only when both entry points are guarded and tested. 11.1 amends ADR-0002 to record the discharge, so plan-012 onward stop carrying it.

The 11.2 fork — close it or accept it

agent_client.dart:155-161 names a confused-deputy risk and says the guard “needs revisiting.” Two honest outcomes; the architect picks one and the cycle executes it. Restating the deferral a third time is not an outcome.

CLOSE — enforce the assumption in code. Bind the principal to the in-flight login so a joiner cannot be authenticated under a different caller’s password. Concretely: capture the principal (or a credential fingerprint — never the password itself, and never logged) when _performLogin starts, and have a joiner verify it matches before joining rather than blindly awaiting. Must preserve the ADR-0013 invariants: _login() stays NOT async (read→call→write in one synchronous turn, so concurrent callers observe a single _loginInFlight), and whenComplete still clears the guard on every path.

ACCEPT — make the assumption enforced by test rather than by hope. Add a test that PINS one-client-per-credential, so a future cycle that reuses an AgentClient across credentials fails immediately. Amend ADR-0013 from a restated deferral to an explicit acceptance with the residual risk stated. Note the current test gap sharply: agent_client_test.dart:312 and app_multipoller_test.dart:76 pin the sharing — the risky direction — and nothing pins the constraint that makes sharing safe.

Prefer ACCEPT unless the architect finds a reachable multi-credential path. The app has exactly one modem, one fixed storage key, and re-auth builds a fresh client (app.dart:275); adding principal-tracking machinery for a situation the architecture forbids is speculative generality, and the ADR-0013 single-sync-turn invariant is delicate enough that touching it for a non-reachable risk is a poor trade. But that is the architect’s call on the evidence, not a foregone conclusion.

Out of scope (plan-011)

  • A7 — switching the client count to /api/network/client-traffic. Deliberately excluded despite being adjacent. Two reasons: it introduces a MAC address into a path deliberately kept count-only (clients_snapshot.dart:8-10), which is a privacy decision the owner should make explicitly rather than inherit from a debt-closure plan; and it depends on an endpoint whose presence on the modem is not verifiable by probe — server.rs:104 runs the bearer check before route(), so a live path, a bogus path and a typo all return 401 identically. Tracked in §Cycle follow-ups.
  • Any base-URL setter UI. 11.1 lands the validator only. A setter is its own security-tier cycle — and a routine one, once the validator exists.
  • A modem WRITE (set_wwandst_monthlimit / set_wwandst_clearday) — triple-blocked (user-demand-gated, no upstream write route, needs hardware verification). Own plan if ever.
  • Cleartext LAN transport. The largest standing security residual and not fixable here: the agent uses tiny_http’s Server::http() with no TLS crate, and the project contract forbids rebuilding the agent. Accepted by ADR-0001 and ADR-0002. The app side of the bargain is implemented and regression-tested (scaffold_test.dart:12-67 guards scoped-not-blanket cleartext), and Uri.parse accepts https unchanged — the app is not the blocker.
  • plan-009 (docs), plan-010 (morph fidelity), the housekeeping plan, and the root-monorepo items.

Standing invariants preserved

  • ADR-0013 single-flight login PRESERVED — _login() stays NOT async (read→call→write in one synchronous turn) and whenComplete clears _loginInFlight on every path, including any new rejection path. 11.1 and 11.2 both touch this file; neither may change the guard’s shape.
  • ADR-0002 base-URL invariant — DISCHARGED by 11.1, not merely carried. The ADR is amended to record it.
  • never-lie — 11.3 is a direct application: the app must not assert a data plan the firmware considers inactive.
  • never-show-0 / last-known + stale honoured — a rejected base URL surfaces as a normal recoverable auth-halt, never a crash, never a fake 0.
  • no PII at rest, no PII in the UI — unchanged; A7, the one item that would relax it, is deliberately out of scope.
  • pure-Dart lib/core boundary upheld (11.1’s client half, 11.2, 11.3). lib/data/ remains its one deliberate exception.
  • no secret committed — 11.4 adds key.properties to the build, never to git (android/.gitignore:12-14 already covers it).
  • no test weakened — every cycle only ADDS tests.

Conventions in play

Every cycle runs through the same disciplined loop, defined in the shared rules under .agents/rules/.

Architect gate

Each cycle carries an architecture-review tier (top, mid, none, or deferred). Legacy provider aliases are normalized while loading. A fresh software-architect returns a GO / NO-GO verdict before RED for the non-trivial ones.

Reviewer separation

REVIEW is performed by a fresh code-reviewer sub-agent — never self-review. Security-tier cycles add a security-reviewer second pass.

NO-DEFER

Every [BLOCKER] and [REFACTOR] finding is resolved in the same cycle’s REFACTOR pass. Scope discipline is not a reason to defer an in-scope finding.
