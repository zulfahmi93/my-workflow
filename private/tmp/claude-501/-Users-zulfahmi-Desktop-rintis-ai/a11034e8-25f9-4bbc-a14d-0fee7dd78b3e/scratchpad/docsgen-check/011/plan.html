11.1

Base-URL validation at both entry points — discharge the ADR-0002 invariant

flutter-expert architect: required (top) security tier Closes: plan-011 — discharges the ADR-0002 bindin…

Land the validator defensively, with no setter UI, and retire a six-plan-old obligation.

Verified at HEAD: credential_store.dart:97 is Future<void> saveBaseUrl(String url) => _storage.write(key: _kBaseUrlKey, value: url); — no scheme check, no host check. agent_client.dart:62 is _baseUrl = baseUrl is Uri ? baseUrl : Uri.parse(baseUrl as String) — equally unguarded. git log -S"isPrivate" is empty across all history; no validator has ever existed.

Implement per §What the base-URL validator must do — that section is this cycle’s specification, read it in full. Summary of the non-negotiables:

  • Both entry points (saveBaseUrl AND the AgentClient constructor). They fail differently and guarding one leaves the other open.
  • Scheme http/https only.
  • Host private/LAN only — RFC1918, link-local, loopback, and the IPv6 equivalents. Public hosts rejected. The hostname-vs-literal-IP question is the architect’s explicit call; default lean is to reject hostnames.
  • Rejection is explicit, never a silent fallback to the default.

Why now, when the risk is not currently reachable. saveBaseUrl’s only caller is a test (credential_store_test.dart:67), no settings UI exists, and a redirect would require direct storage tampering — i.e. device compromise. The invariant is genuinely dormant and correctly gated: plans 002–007 each list a base-URL setter as an out-of-bounds STOP. But it has now been re-carried unfulfilled six times, and its “test-only” property is held by nothing but reviewer vigilance across future plans. Landing the validator converts a standing obligation into a closed one and makes any future settings cycle routine rather than dangerous.

This adds NO setter UI. That remains out of scope and would be its own security-tier cycle.

Preserve ADR-0013. _login() stays NOT async (read→call→write in one synchronous turn); whenComplete clears _loginInFlight on every path including any new rejection path.

Amend ADR-0002 to record the discharge, so plan-012 onward stop carrying the invariant. Record the threat model in the cycle note (attacker-can / mitigation-blocks / residual-risk).

Architecture review. required (top) — SECURITY-TIER — edits the credential store (secret material) and the transport boundary the Bearer password is sent to, and discharges a binding invariant six plans have carried. The architect must confirm: validation runs BEFORE any credential leaves the device; BOTH entry points are covered (guarding only one leaves the other open, and the two fail differently — an unguarded setter persists a bad value forever, an unguarded client sends the password to it); rejection is EXPLICIT failure, never a silent fallback to the default (a silent fallback masks a tampered store and is the subtler bug); the LAN predicate admits every address the modem can legitimately occupy without admitting a public host; and the hostname-vs-literal-IP question is decided explicitly, since a hostname cannot be range-checked without a resolve, which is both a network call inside a validator and a TOCTOU window. Must also confirm the ADR-0013 single-sync-turn _login() invariant survives any new rejection path. Verdict GO/NO-GO ≤ 400 words.

11.2

Resolve the confused-deputy risk — close it or formally accept it

flutter-expert architect: required (top) security tier

agent_client.dart:155-161 documents, in its own words, that the single-flight login guard is safe only under an unenforced assumption:

This is safe only because one AgentClient instance serves exactly one credential for one modem; if this client is ever reused across multiple accounts, a joiner could be silently authenticated under a DIFFERENT caller’s password (a confused-deputy risk) and this guard needs revisiting.

Neither closure route was taken. _login() (:162-169) has no principal check. No test pins the invariant — and the two nearest tests (agent_client_test.dart:312, app_multipoller_test.dart:76) pin the sharing, i.e. the risky direction. ADR-0013:53-56 restates the deferral rather than accepting it.

Take one of the two routes in §The 11.2 fork — close it or accept it. Restating the deferral a third time is not an outcome.

  • CLOSE: bind the principal to the in-flight login so a joiner verifies it matches before joining. Capture a credential fingerprint — never the password itself, never logged.
  • ACCEPT: add a test that PINS one-client-per-credential so a future cycle reusing an AgentClient across credentials fails immediately, and amend ADR-0013 from a restated deferral to an explicit acceptance with the residual risk stated.

Prefer ACCEPT unless the architect finds a reachable multi-credential path. The app has one modem, one fixed storage key, and re-auth builds a fresh client (app.dart:275). Adding principal-tracking for a situation the architecture forbids is speculative generality, and ADR-0013’s single-sync-turn invariant is delicate enough that touching it for a non-reachable risk is a poor trade. The architect decides on the evidence.

Either route must preserve ADR-0013: _login() stays NOT async (read→call→write in one synchronous turn, so concurrent callers observe a single _loginInFlight); whenComplete clears the guard on every path. If CLOSE requires _login() to become async, that breaks the invariant — STOP and escalate rather than trading it away.

Whichever route: the code comment at :155-161 must no longer say “needs revisiting.” Either it is closed, or it points at the ADR that accepted it.

Record the threat model in the cycle note.

Architecture review. required (top) — SECURITY-TIER — the cycle either edits authentication logic (_login/_performLogin) or formally accepts a documented risk in an ADR; both are security decisions and the choice between them is the architect’s. The code itself flags the guard as needing revisiting, and ADR-0013:53-56 restated the deferral rather than accepting it, so a third restatement is not an available outcome. The architect must weigh: is a multi-credential path REACHABLE in this architecture (one modem, one fixed storage key, re-auth builds a fresh client at app.dart:275)? If not, principal-tracking machinery is speculative generality and the ADR-0013 single-sync-turn invariant is delicate enough that touching it for a non-reachable risk is a poor trade — but that judgement is the architect’s on the evidence. Whichever route, the ADR-0013 invariants must survive. Verdict GO/NO-GO ≤ 400 words naming the chosen route.

11.3

Parse plan.enabled — stop rendering a cap the firmware turned off

flutter-expert architect: none

A never-lie violation that fails soft. Upstream zte-agent/src/handlers.rs:197-202 emits four plan fields including enabled (from month_limit_enable). lib/core/data_usage_snapshot.dart:168-177 — parsePlan() — models three: month_limit_bytes, clear_day, remind_percent. Verified: a repo-wide grep for a data-plan enabled in lib/ and test/ returns nothing.

Because the UI keys NO-PLAN exclusively on monthLimitBytes == null (data_usage_section.dart:22), a firmware plan toggled off while month_limit_value remains populated renders a live cap, a percentage, the progress bar, and the OVER/red escalation — for a plan the firmware considers inactive. The app asserts something about the user’s data plan that the device does not agree with.

Read handlers.rs:197-202 yourself and confirm the field name and semantics before parsing it. The backlog’s citation is a lead; the agent source is the contract.

Parse enabled into DataPlan and gate the plan-dependent UI on it: an explicitly-disabled plan presents as NO-PLAN, exactly as an absent limit does today. Decide and document the tri-state — enabled: true, enabled: false, and enabled absent (an older agent). Absent must behave as it does today (fall back to the monthLimitBytes == null test), or the change silently alters behaviour against every agent build that predates the field. That backward-compatibility case is the subtle one and needs its own test.

In-repo precedent: the battery domain already parses charge_limit_enabled and gates on it (battery_snapshot_test.dart:11,18,21). Follow that shape rather than inventing a new one.

This is contract drift against the 5.1 architect lock (cycles/5.1.yaml:53, three fields) that no ADR records as deliberate. Note the correction in the cycle note; amend ADR-0012 if the architect-locked shape is stated there.

Unreachable on the current device (enabled:true), so this cannot be confirmed on hardware without toggling the plan in the modem UI — note that in §Cycle follow-ups rather than blocking on it.

Architecture review. none — Parses one additional boolean from a response the app already consumes and gates presentation on it, with an exact in-repo precedent (the battery domain’s charge_limit_enabled). No auth surface, no secret, no injection sink, no new endpoint. The contract question — the 5.1 architect lock recorded three plan fields, the agent emits four — is resolved by reading the agent source, not by an architecture decision. Correctness gated by an opus code-reviewer pass. NOT security-tier per §Security-tier ruling.

11.4

Real Android release signing config

flutter-expert architect: required (top) security tier

android/app/build.gradle.kts:26-33 verbatim at HEAD:

buildTypes {
    release {
        // TODO: Add your own signing config for the release build.
        // Signing with the debug keys for now, so `flutter run --release` works.
        signingConfig = signingConfigs.getByName("debug")
    }
}

Unchanged since the cycle-1.1 scaffold (749cb7d, the file’s only commit). Debug-key APKs use a well-known password and are machine-local, so this blocks any real distribution.

Half the work already exists: android/.gitignore:12-14 already ignores key.properties, *.jks and *.keystore.

Wire a real release signing config reading from an untracked key.properties. The three properties that matter:

  1. Nothing secret is committed or printed. Not the keystore, not its passwords, not key.properties. Gradle must not echo them in build output either.
  2. Absent keystore → the release build FAILS LOUDLY. Never a silent fallback to the debug key. A fallback recreates the exact defect while appearing fixed, and it would fail in the direction that ships an unsigned-in-practice artifact.
  3. The debug path is unaffected. flutter run and flutter test must keep working with no keystore present — that is the developer default and this cycle must not make local development require key material.

Document the setup (what key.properties needs, where the keystore goes) in the project guide or a build note without leaking any value. Note that the guide is being rewritten by plan-009 cycle 9.1 — if that has landed, add to AGENTS.md; if not, coordinate so the two do not conflict.

Also delete the now-stale applicationId TODO at build.gradle.kts:18 (backlog §D3) — line 18 only; line 30’s signing TODO is the live one this cycle resolves.

This cycle does not produce or distribute a signed build; it makes one possible. Generating the actual keystore is an owner action — an agent must not create key material on the owner’s behalf.

Record the threat model in the cycle note.

Dispose of the plaintext .env

flutter-expert architect: deferred to 11.1 security tier

A plaintext .env (43 bytes) sits in the project root. Verified: correctly gitignored, and read by nothing — there is no flutter_dotenv dependency and the app’s only credential path is flutter_secure_storage. The backlog notes that the ROUTER_PASS* grep hit which flagged it is a prefix false positive against upstream scripts using different identifiers. Hygiene, not exposure.

Read it before deciding. If it contains a live credential it must be treated as such regardless of git status — a gitignored plaintext password on disk is still a plaintext password on disk, and if it is live it should be rotated, which is an owner action.

Then take one of two dispositions, and state which in the cycle note:

  • DELETE if it is genuinely dead. Confirm nothing reads it (flutter_dotenv absent; no Platform.environment or file read of it in lib/, test/, android/, ios/, or any script).
  • KEEP + DOCUMENT if it serves a real local-dev purpose. Then it is named in the project guide’s Local-dev quirks with what it is for, and a .env.example with placeholder values is committed so its shape is discoverable without its contents.

Never commit its contents, and never print them into a cycle note, a commit message, or an agent report. If a value must be referred to, refer to the key name only.

Note the coordination: plan-009 cycle 9.1 rewrites the project guide and its §guide-content-spec already includes mentioning .env in Local-dev quirks. If 9.1 has landed, extend what it wrote; if not, whichever lands second reconciles.

Record the threat model in the cycle note.
