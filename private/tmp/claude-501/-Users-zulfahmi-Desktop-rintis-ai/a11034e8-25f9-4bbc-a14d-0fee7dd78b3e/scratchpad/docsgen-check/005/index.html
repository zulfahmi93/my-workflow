u60-monitor — Data Usage & Data Plan mirror (plan-005)

Surface the modem’s OWN data-management screen — this-cycle usage, the firmware Data Plan (monthly limit), the Clear Date (cycle reset day), and the over-limit warning — as a glanceable, READ-ONLY editorial section, in five file-disjoint TDD cycles: a pure-Dart DataUsageSnapshot (usage + plan) model, binary IEC formatBytes (KiB/MiB/GiB/TiB labels), a DataUsageStatus percent helper, a new DataUsageSection widget whose limit bar ACTIVATES the reserved red token when over-plan, and a poller wired into the screen ABOVE the sticky footer. The limit + reset day are READ from firmware (the agent gains a tiny read-only wrapper over the existing zwrt_data ubus get_wwandst_monthlimit / get_wwandst_clearday) — the app writes NOTHING to the modem. NOT security-tier; ADR-0002 base-URL invariant stays dormant; ZERO new pubspec deps. Every UI cycle MUST invoke the frontend-design:frontend-design skill before writing widget code.

Context

plan-005 mirrors the modem’s native Data-usage screen as a glanceable editorial section. plan-001 shipped live speed, plan-002 the Glance Dashboard, plan-003 the debt tail, plan-004 the editorial restyle. plan-005 surfaces the data-management the firmware ALREADY tracks: usage this cycle, the Data Plan (monthly limit), the Clear Date (cycle reset day), and the over-limit warning — read-only, no app-invented state.

The design pivoted on real evidence. An initial draft assumed the limit had to be app-local (a user-set cap in shared_preferences) because a narrow grep found no quota endpoint. A photo of the modem’s own Data usage screen (Data Used 114.13 GB · Data Plan 45 GB · Clear Date 5 · Data Reminder 75%) proved the firmware owns a real plan + reset day. Re-reading the zwrt_data ubus enumeration in ~/Desktop/tools/open-u60-pro confirmed the methods exist: get_wwandst_monthlimit (the plan), get_wwandst_clearday (the reset day), plus set_* variants. A live probe of the deployed agent nailed the rest:

  • GET /api/data-usage month = this-cycle usage. Live: month.rx_bytes 97.07 GB + month.tx_bytes 17.08 GB = 114.15 GiB used (binary 2³⁰; the modem’s own screen shows the same value loosely as 114.13 GB, confirming its “Data Used” = month rx+tx in binary units, not decimal GB). month == total on this device right now (lifetime ≈ this cycle). The cumulative-counter rule stands: surface as-is, never accumulate, a downward jump is fresh not stale.
  • The plan + reset day are NOT in any existing endpoint — get_wwandst (/api/network/speeds) is real-time session counters, not the plan. So the agent gains a tiny read-only wrapper exposing get_wwandst_monthlimit + get_wwandst_clearday (see §Agent change).
  • Reality: 114.15 GiB used vs a 45 GiB plan ≈ 254% over (the modem’s own screen shows the same values loosely as 114.13 GB / 45 GB = 254%). The over-limit red state is this device’s normal state — the headline case is real, not hypothetical.

READ-ONLY mirror (user-chosen direction). The app DISPLAYS the firmware’s real used / plan / reset-day / reminder and computes the % locally. It writes NOTHING to the modem — no app-local cap, no editor sheet, no shared_preferences. Setting the plan from the app (a set_wwandst_monthlimit write = security-tier) is an explicit FUTURE option, out of scope here (§Out of scope).

NOT security-tier (ruled). (1) ADR-0002 base-URL invariant NOT engaged — no base-URL/credential write; reuses the existing AgentClient. (2) No on-device secret — the plan/reset-day are read from the modem, not stored locally. (3) No modem write — read-only GET /api/data-usage (extended) + pure local % math; no tool-use / state-change / injection sink (numeric u64|null). The architect (5.1) and reviewer (all cycles) confirm this per cycle. Architect gate + ALL review run on opus per the project model-tier policy — a quality choice, not a security requirement.

Five cycles, three batches, file-disjoint, ZERO new pubspec deps. Pure-Dart core first: P5.A model (5.1) ‖ formatBytes (5.2) ‖ DataUsageStatus math (5.3); P5.B the read-only DataUsageSection widget (5.4); P5.C screen integration — extend the data-usage poll parse + wire the section (5.5). One foundational opus architect gate on 5.1 files ADR-0011 + ADR-0012; 5.4/5.5 defer to it; 5.2/5.3 are trivial pure functions (state none). Critical path = 5.1 → 5.4 → 5.5.

One EXTERNAL prerequisite: the agent endpoint. open-u60-pro must extend GET /api/data-usage with a plan block (month_limit_bytes, clear_day, remind_percent) — a tiny read-only wrapper over get_wwandst_monthlimit + get_wwandst_clearday (+ a uci read for the reminder). The Flutter cycles develop against a FAKE stub of that contract (the contract is ours to define), so the app is fully testable before the agent ships; the on-device deploy-pass needs the deployed agent. See §Agent change — the endpoint is now DEPLOYED + live-verified and wireless SSH (dropbear:2222) is in place.

Every UI cycle MUST use the frontend-design skill. Cycles 5.4 and 5.5 each carry a binding instruction: invoke frontend-design:frontend-design BEFORE writing any widget/layout code, and reproduce the locked editorial direction (the DATA section is the structural twin of BatteryTile; the limit bar is a two-tone DL|UL fill — the first on-screen use of the reserved red token). Enforced in each session.prompt and re-checked at REVIEW.

Agent API — verified data source

Confirmed by reading ~/Desktop/tools/open-u60-pro/zte-agent/src/ AND a live probe of the deployed agent. Ground truth for 5.1.

GET /api/data-usage (current) → {ok:true, data:{ day:P, month:P, total:P }}, each P = {tx_bytes, rx_bytes, time_secs, tx_packets, rx_packets} (u64 or null). rx_bytes = download, tx_bytes = upload. Live sample: month.rx_bytes 104229835897, month.tx_bytes 18334831643 → used = rx+tx = 122564667540 B = 114.15 GiB (binary 2³⁰; the modem’s screen labels the same value “114.13 GB”); month == total on this device. Cumulative firmware counters — surface as-is, never accumulate; a downward jump = fresh, not stale.

GET /api/data-usage (EXTENDED by this plan’s agent prerequisite) → adds a plan block:

"plan": { "month_limit_bytes": <u64|null>,   // get_wwandst_monthlimit  (48318382080 B = 45 GiB, labeled "45 GB"; live-verified)
          "clear_day":        <int 1..31|null>,// get_wwandst_clearday    (5 on this device)
          "remind_percent":   <int|null> }     // uci read if present     (75 on this device; null if absent)
Fact Detail
Used (cap basis) month.rxBytes + month.txBytes (the modem’s “Data Used”)
Plan plan.month_limit_bytes — the firmware monthly limit; null when unset / unreadable
Reset day plan.clear_day — the firmware cycle reset day (NOT the calendar 1st; this device = 5)
Reminder plan.remind_percent — the firmware warn threshold; null when not exposed → fall back to 80%
NOT used get_wwandst (/api/network/speeds) is real-time SESSION counters, not the plan

Write is out of scope. set_wwandst_monthlimit / set_wwandst_clearday exist but the app issues ZERO state-changing call (read-only mirror). A future write cycle would be security-tier.

Agent change (open-u60-pro) — external prerequisite

A separate-repo, read-only change to ~/Desktop/tools/open-u60-pro — NOT a Flutter cycle, NOT in this plan’s file-ownership matrix. Extend the existing data_usage handler (zte-agent/src/handlers.rs) to add the plan block by calling the firmware methods that already exist on the zwrt_data ubus object:

  • ubus::call("zwrt_data", "get_wwandst_monthlimit", {"cid":1}) → month_limit_bytes
  • ubus::call("zwrt_data", "get_wwandst_clearday", {"cid":1}) → clear_day
  • ubus::uci_get("…remind…") if a key exists → remind_percent (else null)

Tolerant: any read that fails → that field null (the app degrades gracefully). The exact raw shapes of the two ubus methods are confirmed on-device WHEN implementing this wrapper (ubus call zwrt_data get_wwandst_monthlimit '{"cid":1}'); the agent maps them to the contract above, so the APP never sees the raw ubus shape.

Sequencing + deploy status. The Flutter cycles use a FAKE stub of the extended contract, so they need no live agent. The extended agent is now BUILT, DEPLOYED, and live-verified on the modem — GET /api/data-usage returns the real plan block {enabled:true, month_limit_bytes:48318382080, clear_day:5, remind_percent:75} — on branch add-data-plan-to-data-usage (commit 0d04e0f; not yet PR’d upstream to jesther-ai). Wireless SSH (dropbear on port 2222) is installed + hardened into rc.local, so future deploys need no USB. The only remaining on-device deploy-pass (§Cycle follow-ups) is a human running the built app on a real phone against this deployed agent.

Security-tier ruling — NOT security-tier

Ruling: standard (non-security) cycles; no security-reviewer second pass. (1) ADR-0002 base-URL invariant NOT engaged — no UI or code path sets the base URL; reuses the existing AgentClient. (2) No on-device secret — the plan/reset-day are READ from the modem, nothing is stored locally. (3) No modem write — read-only GET /api/data-usage (extended) + pure local % math; no tool-use / state-change / authorization surface; numeric u64|null parse, no injection sink. Architect gate + ALL review on opus per the model-tier policy (a quality choice, not a security requirement). A FUTURE “set the plan from the app” cycle (set_wwandst_monthlimit) WOULD be security-tier (modem write) — explicitly out of scope here.

Out of scope (plan-005)

  • Writing the plan / reset-day from the app (set_wwandst_monthlimit / set_wwandst_clearday) — read-only mirror only. A future write cycle would be security-tier (modem state change → opus architect + security-reviewer).
  • An app-local cap / shared_preferences — superseded; the limit is firmware-sourced. No on-device storage, no editor sheet.
  • A base-URL / Settings setter — not added (ADR-0002 dormant, carried).
  • Background / push over-limit alerting — OS-infeasible (no LAN push server; per project CLAUDE.md). Over-plan is in-app VISUAL ONLY (the red bar + OVER tag).
  • Decimal/SI units — SUPERSEDED. Volumes render in BINARY IEC units (KiB/MiB/GiB/TiB, 1 GiB = 2^30 B). The modem’s values ARE binary (it stores 45 GiB as month_limit_bytes = 48318382080 and shows it loosely as “45 GB”; its “Data Used 114.13 GB” is likewise GiB). We print the honest IEC “GiB” suffix rather than the modem’s imprecise “GB” (truth over pixel-mirroring). Decimal/SI would both mislabel AND miscompute (~48 “GB”) and disagree with the device.
  • On-device Samsung S22 / iOS device-verify smokes — a manual human deploy pass; the extended agent is already deployed + verified, so this needs only a human running the built app on a device. Tracked in §Cycle follow-ups.

Standing invariants preserved

  • ADR-0002 base-URL invariant DORMANT — no base-URL/credential write (read-only GET).
  • ADR-0009 per-tile freshness EXTENDED — the data-usage tile is a 6th independent Reading, NOT joined to the speed feedState.
  • ADR-0010 sticky footer UNTOUCHED — the section sits ABOVE the Spacer; NO new IntrinsicHeight.
  • Cycle-2.13 no-spurious-scroll + Cycle-4.10 no-RenderFlex-at-1.3× RE-GATED in 5.5 on the shortest target (~360×640).
  • never-show-0 / last-known + stale honoured — em-dash placeholders, StaleFade.
  • pure-Dart lib/core boundary upheld — 5.1/5.2/5.3 import no flutter/material/dart:ui.

Conventions in play

Every cycle runs through the same disciplined loop, defined in the shared rules under .agents/rules/.

Architect gate

Each cycle carries an architecture-review tier (top, mid, none, or deferred). Legacy provider aliases are normalized while loading. A fresh software-architect returns a GO / NO-GO verdict before RED for the non-trivial ones.

Reviewer separation

REVIEW is performed by a fresh code-reviewer sub-agent — never self-review. Security-tier cycles add a security-reviewer second pass.

NO-DEFER

Every [BLOCKER] and [REFACTOR] finding is resolved in the same cycle’s REFACTOR pass. Scope discipline is not a reason to defer an in-scope finding.
